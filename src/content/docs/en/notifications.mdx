# Notifications and email setup

KrakStack separates notification presentation, channel dispatch, and delivery infrastructure. The registry supplies a controlled notification menu, an Effect dispatcher, and a direct Amazon SES channel. Your application owns recipients, authorization, persistence, templates, and delivery policy.

## Choose the parts you need

| Need                     | KrakStack item or export                             | Project responsibility                                   |
| ------------------------ | ---------------------------------------------------- | -------------------------------------------------------- |
| Bell menu and inbox UI   | `notification-menu` or `service-notification/client` | Fetch scoped records, mutate them, and navigate          |
| Channel dispatch         | `service-notification`                               | Compose installed channels and decide when to send       |
| Direct email through SES | `notification-channel-email-ses`                     | Configure AWS, render content, and invoke the dispatcher |
| Durable persistence      | `notification-persistence`                           | Generate migrations, authorize access, and own retention |
| Queued email and retries | Delivery table shipped; worker not shipped           | Own the relay, worker, scheduling, and observability     |

> Do not trust user, organization, or workspace IDs supplied by the browser. Resolve the current actor and authorize every read or mutation at the server boundary.

## Install the notification components

Choose one installation model for the UI.

Install source through the shadcn registry when the component should live in your project:

```bash
bunx shadcn@latest add @krak-stack/notification-menu
```

The item installs `NotificationMenu` under `services/notification/client` and adds its standard shadcn dependencies.

Alternatively, install the package:

```bash
bun add @krak-stack/registry
```

Use the client-only subpath in browser code:

```tsx
import {
  NotificationMenu,
  type NotificationItem,
} from "@krak-stack/registry/service-notification/client";
```

The umbrella export is also available when a module needs the UI and dispatcher together:

```ts
import {
  NotificationMenu,
  NotificationService,
} from "@krak-stack/registry/notifications";
```

If package components are rendered in your application, include the package Tailwind source:

```css
@import "@krak-stack/registry/tailwind.css";
```

## Connect the menu to project data

`NotificationMenu` is controlled by data and callbacks. It does not fetch, cache, or authorize records.

```tsx
import { NotificationMenu } from "@krak-stack/registry/service-notification/client";

export function WorkspaceNotifications({ notifications }) {
  return (
    <NotificationMenu
      notifications={notifications}
      onMarkRead={(notificationIds) =>
        notificationClient.markRead({ notificationIds })
      }
      onArchive={(notificationIds) =>
        notificationClient.archive({ notificationIds })
      }
      onNavigate={(notification) => {
        if (notification.href) window.location.assign(notification.href);
      }}
    />
  );
}
```

Each item supports:

- `id` and `title`
- optional `description`, `href`, `createdAt`, and `timestampLabel`
- `readAt` for unread presentation
- `archivedAt` for inbox/archive placement

Opening the menu reports all unread inbox IDs to `onMarkRead`. Set `markReadOnOpen={false}` if your product uses item-level read behavior. `onArchive` receives either one item ID or every current inbox ID.

Use `renderItem` or `renderTrigger` to change presentation without coupling the registry component to your router or domain. Pass `locale` or `messages` to override the built-in English and French menu chrome.

## Define the trusted server contract

The browser should submit only record IDs and intent. The server derives actor and scope from the authenticated request.

```ts
type NotificationClient = {
  list: (input: {
    state: "inbox" | "archive";
  }) => Promise<readonly NotificationItem[]>;
  markRead: (input: { notificationIds: readonly string[] }) => Promise<void>;
  archive: (input: { notificationIds: readonly string[] }) => Promise<void>;
};
```

For every operation, the server should:

1. Resolve the authenticated actor.
2. Resolve the active organization and workspace from trusted session context.
3. Verify that every requested notification belongs to that recipient and scope.
4. Apply the mutation and return only authorized records.
5. Invalidate or refresh the matching client query.

## Add the notification dispatcher

Install the Effect service through source:

```bash
bunx shadcn@latest add @krak-stack/service-notification
```

Or import it from the package:

```ts
import { NotificationService } from "@krak-stack/registry/service-notification";
import { NotificationChannelRegistry } from "@krak-stack/registry/service-notification/channels";
```

`NotificationService` dispatches each top-level message key to every installed channel with the same key. This keeps event policy separate from providers.

```ts
import { Effect, Layer } from "effect";
import { NotificationService } from "@krak-stack/registry/service-notification";
import { NotificationChannelRegistry } from "@krak-stack/registry/service-notification/channels";

const channels = NotificationChannelRegistry.layer([
  {
    key: "inApp",
    send: (payload) => persistInboxNotification(payload),
  },
]);

const notificationLayer = NotificationService.layer.pipe(
  Layer.provide(channels),
);
```

Project channels can augment `NotificationChannels` so `send` remains typed. Keep event definitions in project source, because event names and payloads are domain policy rather than registry policy.

## Configure direct SES email

Install both registry items:

```bash
bunx shadcn@latest add \
  @krak-stack/service-notification \
  @krak-stack/notification-channel-email-ses
```

Set the required server environment variables:

```dotenv
SES_REGION=ca-central-1
SES_ACCESS_KEY_ID=...
SES_SECRET_ACCESS_KEY=...
NOTIFICATION_EMAIL_FROM=Example <no-reply@example.com>
```

Compose the SES channel into the dispatcher:

```ts
import { Effect, Layer } from "effect";
import { NotificationService } from "@krak-stack/registry/service-notification";
import { NotificationChannelRegistry } from "@krak-stack/registry/service-notification/channels";
import { SesNotificationChannel } from "@krak-stack/registry/notification-channel-email-ses";

const channels = Layer.effect(
  NotificationChannelRegistry,
  Effect.gen(function* () {
    const email = yield* SesNotificationChannel;
    return NotificationChannelRegistry.make(email);
  }),
).pipe(Layer.provide(SesNotificationChannel.layer));

export const notificationLayer = NotificationService.layer.pipe(
  Layer.provide(channels),
);
```

Send rendered text or HTML:

```ts
const program = Effect.gen(function* () {
  const notifications = yield* NotificationService;

  yield* notifications.send({
    email: {
      to: "volunteer@example.com",
      subject: "Application approved",
      text: "Your volunteer application was approved.",
      html: "<p>Your volunteer application was approved.</p>",
    },
  });
});
```

The SES payload also supports `from`, `cc`, `bcc`, and `replyTo`. At least one of `text` or `html` is required. A payload-level `from` overrides `NOTIFICATION_EMAIL_FROM`.

Direct SES delivery is appropriate for simple or non-critical messages. It runs inline in the calling process and does not provide a durable outbox, application-level scheduled retries, or an administrative delivery log.

## Install durable notification persistence

Install editable source from the shadcn registry:

```bash
bunx shadcn@latest add @krak-stack/notification-persistence
```

Or import the server-only npm module:

```ts
import {
  notificationDeliveries,
  notificationSettings,
  notifications,
} from "@krak-stack/registry/service-notification/persistence/drizzle";
import { decodeNotificationDeliveryPayload } from "@krak-stack/registry/service-notification/persistence/schema";
```

The module ships three PostgreSQL tables:

| Table                     | Purpose                                                                          |
| ------------------------- | -------------------------------------------------------------------------------- |
| `notifications`           | Recipient-specific inbox snapshots with read and archive timestamps              |
| `notification_settings`   | Channel preferences scoped by recipient, organization, workspace, and event      |
| `notification_deliveries` | Channel-neutral outbox snapshots, scheduling, claims, retries, and final results |

Re-export installed source from your project's Drizzle schema entry:

```ts
export * from "@/services/notification/persistence/drizzle";
```

Then generate and commit a migration in the receiving project. KrakStack distributes reusable definitions rather than shared migration history, so each project controls rollout and future schema changes.

Store external identity and organization IDs as text unless the identity tables are in the same database. Do not add cross-database foreign keys.

Persist the following scope on each inbox record:

- recipient user ID
- organization ID when applicable
- workspace or audience
- event key and version
- title, description, and destination snapshot
- created, read, and archived timestamps

For delivery records, store one row per channel with a stable idempotency key and a versioned payload snapshot. Email payload version 1 stores SES-compatible recipients, subject, text, and HTML. Keep template implementations in source control. Retrying a delivery should send the persisted snapshot instead of rendering a potentially changed template.

The Effect codec rejects unsupported channel and payload-version combinations. Add a new codec variant before writing a new payload version, and retain old variants while historical rows remain.

> KrakStack ships table definitions and codecs, not authorization queries, CRUD operations, migrations, an outbox relay, a worker, or an administrative delivery UI. Effect workflow and persisted-queue tables remain Effect-owned infrastructure.

## Queue email safely

The following flow is application-owned. When email must survive process crashes:

1. In the same database transaction as the domain change, insert the in-app notification and a queued `notification_deliveries` record.
2. Commit the transaction before offering work to the queue.
3. Let an outbox relay recover committed deliveries that were not offered because the process crashed.
4. Queue a versioned job containing only `{ deliveryId }`.
5. Have the worker lease the delivery record, decode and send its persisted snapshot, and store the provider result.
6. Schedule application retries through `scheduledFor`; reserve queue retries for infrastructure failures.

Do not compose both a direct SES channel and a queued email channel under the same `email` key in the web process. `NotificationService` invokes every matching channel, so that composition would send duplicates. The web process should enqueue; only the worker should invoke the SES transport.

## Apply preferences and localization

Decide preferences before creating optional channel work:

- Persist in-app notifications only when the in-app channel is enabled.
- Enqueue optional email only when the email channel is enabled.
- Do not allow preferences to suppress transactional or legally required messages unless product policy explicitly permits it.

Resolve the recipient locale at publication time. Render source-defined email templates in that locale, then persist the rendered snapshot. Notification menu chrome is localized independently through the component's `locale` and `messages` props.

## Production checklist

- Authorize list, read, and archive operations on the server.
- Include recipient, organization, and workspace scope in every query and mutation.
- Keep browser exports separate from database, AWS, and worker modules.
- Verify SES identities, sandbox status, sending limits, and least-privilege credentials.
- Make event keys and queue payloads versioned.
- Make worker claims concurrency-safe and idempotent.
- Record attempts, provider IDs, failures, and final delivery status.
- Test English and French menu copy and email snapshots.
- Test process crashes between database commit, queue offer, and provider response.
- Never log credentials or sensitive message bodies.
